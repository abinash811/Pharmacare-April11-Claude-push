# PharmaCare Database

## Why this exists

Schema changes and query patterns are the hardest class of mistake to
undo in production — a bad migration or a missing index doesn't show up
until real data volume hits it. This skill exists because "it worked
locally with 20 rows" has never once caught the actual problem.

## Before you start

Read `CLAUDE.md`'s Manifesto rule 6 (soft deletes only) and
`docs/09_DATABASE.md`'s migration rules if you haven't this session.

## Non-negotiables — exact steps, no substitutions

1. **All schema changes go through Alembic migrations.** Never
   `ALTER TABLE` manually, never edit a model and assume the DB catches
   up. `cd backend && venv/bin/alembic revision --autogenerate -m "..."`,
   review the generated migration file before applying it, then
   `venv/bin/alembic upgrade head`.
2. **Never hard `DELETE` from any table.** Soft delete via `deleted_at`.
   This applies to migrations too — a migration that drops rows is a bug.
3. **Review every autogenerated migration by hand** before applying it.
   Alembic's autogenerate can miss renames (sees them as drop+add,
   destroying data) or miss server-side defaults — read the generated
   file, don't just run it.
4. **Naming follows `docs/16_NAMING_CONVENTIONS.md`** — table names,
   column names, index names, all consistent with what's already there.

## Query performance workflow

The `postgres` MCP tools connect to the local dev database in restricted
(read-only-safe) mode — use them instead of guessing:

```
- [ ] Step 1: Read docs/09_DATABASE.md for the real schema of the tables involved
- [ ] Step 2: Write the query
- [ ] Step 3: Run explain_query (postgres MCP) to see the actual query plan
- [ ] Step 4: If it's doing a sequential scan on a large table, run analyze_query_indexes to check what index would help
- [ ] Step 5: Add the index via a real Alembic migration (never CREATE INDEX by hand outside one)
```

For a broader health check across the whole schema, `analyze_db_health`
and `analyze_workload_indexes` (also `postgres` MCP) surface missing
indexes and bloat across every table, not just the one query you're
looking at — worth running periodically as tables grow, not just when
something already feels slow.

**Never point any of these tools at a production connection string.**
Local/staging only — this is a settled decision, not something to
reconsider per-task.
